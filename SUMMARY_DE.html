Kapitel 1

Mission & Positionierung

Der Emporix Journey Aware Storefront (intern „Showcase") ist eine produktionsreife Referenz-Storefront für die headless-B2B-Commerce-Plattform Emporix. Bewusst als Fundament, nicht als fertiges Produkt positioniert.

Head-Start statt Endpunkt

Vorgebaute MVP-Flows (Browse, PDP, Cart, Checkout, Login, Register, Order-History) zeigen „den richtigen Weg" — aber das README sagt klipp und klar: „Nicht alles ist vorgebaut. Wir wollen ein solides Fundament, kein Fertigprodukt."

README §What to Expect

Komponierbar by Design

Pricing, Suche, CMS, Payment, Approval und Quote sind hinter Interfaces austauschbar. Vendor-SDKs sind Integrationen, niemals Kern. Switch zwischen Emporix-Search und BatteryIncluded oder zwischen Storyblok und JSON-CMS = nur Env-Flip.

ADR 0001

B2B-first

Account-Management, Service-Portal, Approval-Workflow (Beta), Quote-/Offer-Management (Beta) und Customer-Segment-Pricing differenzieren den Showcase vom üblichen B2C-Demo.

Beta-Features

Performance-Budget Lighthouse 90+

RSC-by-default, präzise Cache-Header, Image/Font-Optimization und ein hartes Verbot, dass der Browser jemals DI-Container importiert (sonst Bundle-Bombe).

Kapitel 2

Architektur-Überblick

Die Anwendung ist ein „Backend in the Frontend": ein klar geschnittener Next.js-App-Router-Layer auf drei DI-verdrahteten Plattform-Schichten. Browser und Server sind durch eine harte /api/*-Naht getrennt.

Systemskizze · Browser oben (kein DI), App-Router mittig (Layout-Gruppen + Middleware-Kette), Plattform-Schichten unten mit generierter Inversify-Verdrahtung

Kapitel 5

Dependency Injection (InversifyJS · code-generiert)

Die DI-Bindings werden nicht von Hand geschrieben. Der Generator scripts/di-generator.ts scannt src/platform/ und emittiert die Container. Hot-Reload via npm run generate:watch.

server.ts

import 'server-only' · Node-Runtime · Zugriff auf headers(), Web-Push-Backend, Service-Tokens

ssr.ts

import 'server-only' · RSC-/Streaming-sicher · keine Node-only-APIs

client.ts (opt-in)

Nur wenn NEXT_PUBLIC_ENABLE_DI_GENERATE_CLIENT=true · Default: aus · Browser nutzt lib/client/* + fetch('/api/*')

Sicherheits-Default

Suffix-Klassifizierung

Suffix Landet in Anmerkung
*Server server.ts Node-only, Headers, Cookies, Service-Tokens
*SSR ssr.ts RSC-safe, keine Node-only-APIs
*Client client.ts (opt-in) Auditiertes Browser-Bundle · selten nötig
kein Suffix alle Container Pure Logik, Runtime-agnostisch

Aliases & Extensions

depency.yml (sic) lässt Vendor-Bindings zur Build-Zeit swappen, ohne Call-Sites zu ändern. Das extensions/-Verzeichnis ist ein Plugin-System per plugin.json — Adapter oder Services können dort registriert werden, ohne den Application-Core zu berühren. 

// Service definieren
@injectable('CartService', 'Singleton')
class EmporixCartService implements CartService {
  constructor(@inject('CartApi') private api: CartApi) {}
  // …
}

// Generator erkennt den Decorator automatisch beim
// `npm run generate` / `dev` und schreibt die Binding
// passend in server.ts / ssr.ts (Suffix → Runtime).

Kapitel 7

CMS-Subsystem — strikt adapter-basiert

Der architektonisch markanteste Teil. Geregelt durch ADR 0001 (Provider nur über Adapter) und ADR 0002 (Komponenten co-located & schema-first). Schalten zwischen Storyblok und dem lokalen JSON-CMS ist ein reiner Env-Flip.

Eine zentrale Render-Pipeline · Provider tauschbar als reiner Daten-Übersetzer · Renderer kennt keinen Provider

Die SPI

interface CmsAdapter {
  readonly id: string;
  hasContent(): boolean;

  getPage(slug, locale, site)
    : Promise<CMSPage | CMSNoResult>;

  getNavigation(locale, site)
    : Promise<CMSNavigation | CMSNoResult>;

  // optionaler Provider-Editing-Surface:
  getEditableProps?(c: CMSComponent)
    : HTMLAttributes<HTMLElement>;

  BridgeScript?: ComponentType;
}

Mitgelieferte Adapter

StoryblokCmsAdapter Storyblok REST + Visual-Editor
LocalJsonCmsAdapter src/data/cms/<site>/<locale>/<slug>.json
NoneCmsAdapter leere Fallback-Quelle · App startet immer
FallbackCmsAdapter Composite: Primary + Default-Site-Fallback

Drift-Guards (als Code erzwungen)

  • renderer-provider-agnostic.drift.test.ts failt den Build, wenn der zentrale Renderer oder Shell aus @/platform/integrations/* importiert
  • getCmsService-Lazy-Bind-Vertrag · safe across Turbopack module-graph split
  • Browser-Bundle-Smoke (verify:client-chunks) auditiert, dass kein Storyblok-Token in Client-Chunks geleakt wird
Kapitel 8

Authentifizierung & Sessions

NextAuth v5 als Frontend-Schicht, aber die Wahrheit über User & Berechtigungen liegt im Emporix-Backend. Die Showcase delegiert AuthZ vollständig dorthin.

Vier Token-Typen

Token-Typ Scope Caching
Public Storefront-API-Key globalThis-Cache, ~3200s TTL
Anonymous Guest-Carts Per Session
Customer Eingeloggter User Per Session
Service Privilegierter Backend-Call Nur Server-RAM, Key inkl. Secret

Thundering-Herd-Schutz per Promise-Dedup.

SSO-Passwort-Flow

  1. User authentifiziert mit SSO-Provider (Google, Azure AD, …)
  2. Auth.js validiert & liefert E-Mail
  3. Server berechnet deterministisches Passwort: sha256(NEXT_AUTH_SSO_SECRET + email)
  4. Dieses Passwort wird bei Emporix als „normales" Credential verwendet
  5. Session wird sowohl in Auth.js als auch in Emporix etabliert

Skript: npm run generate:sso-password

Cookies & CSRF

  • Emporix-Token base64 in httpOnly-Cookie
  • Service-Token bewusst nur im Server-RAM
  • Eigenes /api/csrf-Endpoint setzt httpOnly-Cookie
  • CSRF-Verifikation derzeit nicht überall lückenlos (Doku-Flag)

Bekannte Schwächen

  • API-Routes prüfen keine eigene Auth — komplett an Emporix delegiert
  • src/lib/client/auth.ts referenziert nicht-existente /api/auth/login|logout|session (toter Code)
  • /api/setup: Bearer-geschützt, aber String-Vergleich nicht timing-safe
  • Session-Invalidation während SSR kann Client uninformiert lassen (Cookie-Write-Fenster verloren)
Kapitel 9

State Management

Zustand — der einzige aktive Store

12 Stores in src/stores/ für Cart, Session, Notifications, Dashboard-Layout, Search-Facets, etc. Stores werden nicht als Singletons exportiert — sondern als Context-bound Factories, um SSR-Cross-Request-Leaks zu vermeiden.

Per-Request Store Factory

Cross-Store-Sync

Wenn zwei Stores sich gegenseitig informieren müssen (z.B. Session-Switch invalidiert Cart), passiert das über explizite Subscribers, nicht über implizite Abhängigkeiten. Verhindert Render-Storms und macht Debugging deterministisch.

Inaktiv

react-redux und @preact/signals-react sind installiert, aber im Code nicht referenziert. Sie sind Kandidaten für ein npm uninstall-Cleanup.

Dead Deps

Provider-Stack

9 React-Provider müssen in einer festen Reihenfolge nesten (i18n → Theme → SiteProvider → Auth-Session → Stores → CSRF → Notifications → CMS → AppShell). Dokumentiert als fe_provider-bootstrap in der Memory.

Kapitel 16 · Aktueller Stand

Branch feature/SHOW-323 — Storyblok-Hardening

Der aktive Branch bündelt einen mehrwöchigen Sweep, der den Storefront von „Storyblok-gekoppelt" zu „CMS-provider-agnostisch" gemacht hat — ohne Änderungen außerhalb des cms/-Subsystems. Die ADRs 0001 und 0002 sind dabei ratifiziert worden.

Phase Was landete
A · EMP-21 Umbenennung NEXT_PUBLIC_{CMS,STORYBLOK_*}_* → NEXT_* (nur server-side)
B Bridge-Bootstrap in Server-Action verschoben — keine Client-Token-Exposure
C Top-Banner-Fetch refactored: fetchTopBanner + sicherer use-banner-Hook
D Per-Site-Theming + Browser-Smoke für Theme-Applikation
E CMS-Webhook + HMAC + gezielte Cache-Invalidation
F Provider-agnostische Preview-Route via SPI-Split
G Composite Default-Content-Fallback + Production-Build-Smoke
EMP-21 Final AST-Loophole geschlossen: computed access & destructuring sind jetzt durch ESLint + Browser-Bundle-Smoke verboten
ADR 0001 (Adapter-only) + 0002 (Component co-location) ratifiziert

Das Litmus-Ergebnis: Der Wechsel zwischen Storyblok und LocalJson-CMS ist jetzt ein reiner Env-Flip. Keine Imports werden ausgetauscht, kein Application-Code wird angefasst, kein Token leakt ins Client-Bundle.
